# Clearance challenge review and three-minute story

Accepted consulting scope, November 14. Application implementation is in progress; the test plan records measured acceptance separately from this recording choreography.

## Self-assessment

The first draft overemphasized visible classification levels and underemphasized incompatible client compartments. A higher clearance does not solve cross-client contamination. Generic landing-page content was weak software-factory evidence, and a large graph risked showing machinery instead of a client result. The previous estimate also preceded live service access.

Three adversarial reviewers independently identified immutable engagement binding as the simplification. Their suggested consulting briefs improved the human stakes but did not sufficiently answer the subsequently verified pass/fail software-building theme. Root therefore narrowed the artifact to two generated, tested, executable approval workflows.

## Expert questions that changed the design

- Security architect: can the wrong client's text reach the model before a policy check? Fixed collections and canonical-ID admission precede context construction.
- Information-flow reviewer: can a cleared worker carry its previous client's history into a new engagement? Existing run cannot change engagement; reassignment starts a fresh context.
- Consulting delivery lead: does the result work for the right client, and can a partner's dual access accidentally merge work? Only a non-model operator manages both lanes; artifacts retain client ownership.
- Software-factory judge: what software was actually created and tested? Model produces a bounded executable workflow configuration; the client app runs it and independent cases check behavior.

These are expert lenses and reviewed design reasoning, not interviews or endorsements from industry experts. NIST's attribute-based authorization guidance supports separating ownership, sensitivity and requested action.
